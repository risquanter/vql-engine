# ADR-025: Order-Independent Evaluation

**Status:** Accepted
**Date:** 2026-11-15
**Tags:** evaluation, sampling, determinism, runtime-model, consumer-contract

---

## Context

- A Scala `Set` iterates in an order derived from its elements' `hashCode`.
  That order is fixed across runs only when `hashCode` is computed from the
  element's content.
- A dispatcher may refuse a predicate or a function for some arguments.
- An evaluator that evaluates the left operand first and passes on its
  failure makes `p ∧ q` and `q ∧ p` differ once a refusal occurs. A
  quantifier that stops at the first failure makes its result depend on the
  domain's iteration order.
- Fisher-Yates selection with a deterministic generator fixes positions. The
  elements at those positions depend on the population's order.
- `Value.raw` is `Any`, so only the consumer knows a carrier's type and how
  to order it.

---

## Decision

### 1. A dispatcher refusal is an unknown truth value

Evaluation combines truth values under Kleene's strong three-valued logic.
An operator gives a known value whenever that value is the same for every way
the unknown could resolve, and unknown otherwise (`U` is unknown):

| `p` | `q` | `p ∧ q` | `p ∨ q` | `p → q` | `p ↔ q` |
|---|---|---|---|---|---|
| T | U | U | T | U | U |
| F | U | F | U | T | U |
| U | T | U | T | T | U |
| U | F | F | U | U | U |
| U | U | U | U | U | U |

`¬U` is `U`. `∀` is false if any binding is false, otherwise unknown if any
binding is unknown, otherwise true. `∃` is the dual. An operand that decides
the result alone stops evaluation, so a model with no refusals is evaluated
exactly as under two-valued logic.

### 2. Only a dispatcher refusal is unknown

`EvaluationFailure.PredicateRefused` and `EvaluationFailure.FunctionRefused`
become unknown. A function refusal makes the atom holding the function
unknown. Every other failure, such as `VariableSortMismatch`,
`UnboundVariableError` or `DomainNotFoundError`, stops evaluation at once.

### 3. An unknown range or scope fails with its refusal

The range and the scope each decide one element's membership. An unknown
truth value leaves membership undecided, so evaluation returns the refusal
that made it unknown. When several refusals are met, the first in
evaluation order is returned.

### 4. A domain holds its elements in an order the consumer declares

```scala
final case class OrderedDomain private (carriers: Vector[Any])

object OrderedDomain:
  def of[A](carriers: Iterable[A])(using ordering: Ordering[A]): OrderedDomain

case class RuntimeModel(domains: Map[TypeId, OrderedDomain], dispatcher: RuntimeDispatcher)
```

`of` removes equal carriers and sorts the rest. It requires that `ordering`
ranks no two distinct carriers equal, because such a pair would keep its
input order.

### 5. Evaluation and sampling read the declared order

Range extraction, scope evaluation, `satisfyingSet` and every quantifier walk
a domain in its declared order. Every sampling entry takes its population as
an `IndexedSeq`, and the typed pipeline passes the range in domain order.

### 6. New evaluation code follows 1 and 5

- A new connective or quantifier combines unknown values under §1's tables.
- A new walk over a domain, or a new sampling entry, reads the declared
  order.

## Code Smells

### ❌ Passing on a refusal before the other operand is evaluated

```scala
// BAD: q(x) ∧ r(x) fails where r(x) ∧ q(x) answers.
evalFormula(p, env, model).flatMap {
  case false => Right(false)
  case true  => evalFormula(q, env, model)
}

// GOOD: an unknown left operand still lets the right one decide.
evalFormula(p, env, model).flatMap {
  case Truth.Known(false) => Right(Truth.Known(false))
  case left               => evalFormula(q, env, model).map(conjoin(left, _))
}
```

### ❌ Sampling from a `Set`

```scala
// BAD: the elements at the shuffled positions follow the Set's hash order.
sampler.sample(rangeElements.toSet, n)

// GOOD: the range in its domain's declared order.
sampler.sample(rangeElements, n) // rangeElements: Vector[Value]
```

### ❌ An ordering that ranks distinct carriers equal

```scala
// BAD: two handles with the same length keep their input order.
OrderedDomain.of(handles)(using Ordering.by(_.name.length))

// GOOD: an ordering on a key that identifies the carrier.
OrderedDomain.of(handles)(using Ordering.by(_.id))
```

## Cross-ADR Relationship

- **ADR-017.** The range is read as set algebra: `∧` an intersection and `¬`
  a complement. That reading holds for every result evaluation returns,
  because an element whose membership is unknown fails evaluation and never
  enters a set. Range extraction stays exhaustive (ADR-017 §2).
- **ADR-003.** A sample is reproducible for a population in the same order.
  The domain's declared order supplies that order to the typed pipeline.
- **ADR-001 and ADR-012.** `RuntimeModel` still validates dispatcher coverage
  and domain registration once. The tie check is a `require` on what an
  `OrderedDomain` is, and evaluation keeps its `Either` channel.

## Alternatives Rejected

### Strict evaluation
- **What:** any refusal anywhere fails the query.
- **Why rejected:** it removes short-circuiting from every evaluation, so an
  inner `∃` always scans its whole domain. A model with one missing value
  can no longer answer a query that never needed that value.

### Totality as a documented precondition
- **What:** keep left-first evaluation and require dispatchers never to
  refuse.
- **Why rejected:** both order dependences remain for every consumer whose
  dispatcher can refuse.

### An order map beside the domains
- **What:** `domainOrders: Map[TypeId, DomainOrder]` beside
  `domains: Map[TypeId, Set[Value]]`, applied when the `FolModel` is built.
- **Why rejected:** the two maps can disagree, each value is read back
  through `Extract` only to be compared, and the evaluation entries would
  have to take a `FolModel` to reach the sorted domains.
