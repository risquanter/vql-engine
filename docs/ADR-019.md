# ADR-019: Structured Bind-Error Detail across the Error/Typed Boundary

**Status:** Accepted
**Date:** 2026-08-17
**Tags:** error-handling, layering, bind-phase, boundary, consumer-contract

---

## Context

- The error layer must not depend on the typed layer, where sort identity
  (`TypeId`) and the structured `TypeCheckError` live. Any sort information a
  bind failure carries must therefore cross that boundary as a primitive, not
  as a typed value.
- A consumer that maps bind failures to distinct outcomes by **sort** (a token
  that fails to parse as one sort is a recoverable reference mistake; the same
  failure on another sort is a genuine type error) needs the sort for each
  error at the high-level entry point — without dropping to the low-level
  binder and duplicating the engine's rendering.
- Rendering a structured type error to a human string and discarding its sort
  at that step forces every sort-sensitive consumer to either re-derive the
  sort out of band or re-render the message, producing two sources of the same
  string that drift apart.
- A consumer's recoverability boundary — which subset of errors is a
  user-recoverable reference mistake — need not coincide with any single error
  kind. Co-locating each error's sort with its own rendered message lets the
  consumer apply its own predicate over one flat list, rather than depending on
  the whole list being homogeneous.
- The message contract — a list of human-readable strings — must stay available
  unchanged for consumers that read only text.

---

## Decision

### 1. Primitive-only detail type in the error layer

A per-error `enum` in `vql.error` carries the sort as a `String` and each
case's own rendered message. It imports nothing from `vql.typed`.

```scala
package vql.error

enum BindErrorDetail:
  case UnparseableConstant(name: String, sortName: String, sourceText: String, rendered: String)
  case Other(rendered: String)

  // `rendered` is stored, not derived, so it is an abstract member the case
  // parameters implement. A concrete `def rendered` matching on the cases
  // would clash with the same-named parameter (ADR-006 §3) and not compile.
  def rendered: String
```

### 2. `BindError` holds one representation; the message list is derived

`BindError` carries the structured details and derives the string contract from
them, so the two never drift.

```scala
case class BindError(details: List[BindErrorDetail]) extends QueryError:
  def messages: List[String] = details.map(_.rendered)
  def message = s"Query type-checking failed: ${messages.mkString("; ")}"
```

### 3. One per-error renderer is the single source of rendered strings

Rendering is a per-error `renderTypeError(TypeCheckError): String`; the detail's
`rendered` and the message list both flow from it. No second rendering path.

```scala
private def renderTypeError(e: TypeCheckError): String = e match
  case TypeCheckError.UnparseableConstant(_, sort, src) => s"cannot parse '$src' as ${sort.value}"
  case /* … one arm per TypeCheckError case … */        => ???
```

### 4. Conversion lives in the layer that already sees both sides

The `TypeCheckError → BindErrorDetail` fold runs in the facade
(`vql.semantics`), which already imports both layers. The sort crosses there as
`sort.value` — the sanctioned primitive read of the opaque `TypeId` (ADR-015).

```scala
private def toBindErrorDetail(e: TypeCheckError): BindErrorDetail = e match
  case TypeCheckError.UnparseableConstant(name, sort, src) =>
    BindErrorDetail.UnparseableConstant(name, sort.value, src, renderTypeError(e))
  case _ => BindErrorDetail.Other(renderTypeError(e))
```

## Code Smells

### ❌ Reaching into the typed layer from the error layer

```scala
// BAD: BindError carries typed values; vql.error now depends on vql.typed
case class BindError(errors: List[vql.typed.TypeCheckError])

// GOOD: primitives only; the sort crosses as a String
case class BindError(details: List[BindErrorDetail])
```

### ❌ A parallel string list beside the details

```scala
// BAD: two fields for the same errors drift apart
case class BindError(details: List[BindErrorDetail], messages: List[String])

// GOOD: one representation, the string list derived
case class BindError(details: List[BindErrorDetail]):
  def messages: List[String] = details.map(_.rendered)
```

### ❌ Re-rendering the message in the consumer

```scala
// BAD: the consumer re-derives the BIND_FAILED text the engine already rendered
val text = detail match { case UnparseableConstant(n, s, _, _) => s"cannot parse '$n' as $s" }

// GOOD: read the rendered string the detail carries
val text = detail.rendered
```

### ❌ Discarding the sort at the render step

```scala
// BAD: sort is gone after rendering, so the consumer bypasses the facade
val strings = renderTypeErrors(errors) // sort lost; consumer must call QueryBinder.bind

// GOOD: keep the sort beside its message in one detail
val details = errors.map(toBindErrorDetail)
```

## Cross-ADR Relationship

- **ADR-004.** The `vql.error → vql.typed` prohibition is preserved:
  `BindErrorDetail` has only `String` fields and the conversion runs in the
  facade, the layer that already imports both. No new import direction is added.
- **ADR-006.** `BindErrorDetail` is a pure-data sum whose cases share one
  `rendered` accessor → `enum`. `QueryError` stays a `sealed trait` because its
  variants override `formatted`/`context` with distinct bodies; `BindError`
  remains a `case class` variant of it.
- **ADR-012.** `BindError` is still returned on the `Either` left channel; the
  `require`-vs-`Either` policy is untouched.
- **ADR-015.** The sort crosses as `TypeId.value`, the sanctioned primitive read
  of the opaque type — no `asInstanceOf`, no new carrier.

## Implementation

| Location | Pattern |
|---|---|
| `vql/error/QueryError.scala` | `enum BindErrorDetail` (primitives); `BindError.details` + derived `messages` |
| `vql/semantics/VagueSemantics.scala` | `renderTypeError` (per-error), `toBindErrorDetail`; both `BindError` construction sites |
| `vql/semantics/VagueSemanticsTypedSpec.scala`, `SatisfyingSetSpec.scala` | read `messages`; new sort-fidelity tests |

## Alternatives Rejected

### E2 — a dedicated homogeneous `UnparseableConstantError` variant
- **What:** emit a new `QueryError` variant only when **every** bind error is an
  `UnparseableConstant`; any mix folds to `BindError`.
- **Why rejected:** its "all `UnparseableConstant`" grouping does not match a
  consumer's "all node-recoverable" boundary. A homogeneous non-node unparseable
  (a bad `Loss`/`Probability` literal, reachable because those sorts have
  validators) lands in the variant and either drops the rendered message —
  forcing the re-render this ADR removes — or carries the rendered string per
  item, at which point it is this decision with an extra precondition and no
  simplification.

### E3 — relocate `TypeCheckError`/`TypeId` into `vql.error`
- **What:** move the typed error and sort types down so `BindError` carries
  `List[TypeCheckError]` directly.
- **Why rejected:** it inverts the ADR-004 layering — `TypeId` is the core of the
  type system, and pulling it into the error layer makes the low, stable error
  vocabulary depend on the type system, breaking the property that every layer
  returns a uniform `Either[QueryError, A]` (ADR-012). The relocation is also
  disproportionate to the need: the demonstrated requirement is one primitive
  (the sort name, as a `String`) for one consumer on one error kind, which the
  facade projection satisfies without moving any type. E3 becomes the natural
  design only if consumers come to need rich, structured, multi-sort bind-error
  analysis; at that point this decision is revisited. The refactor size is a real
  cost but is not what settles it — the layering inversion and the
  disproportion-to-need are.
