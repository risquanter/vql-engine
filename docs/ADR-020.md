# ADR-020: Binder Error Accumulation across Independent Subtrees

**Status:** Accepted
**Date:** 2026-08-18
**Tags:** error-handling, type-checking, bind-phase, accumulation

---

## Context

- `QueryError.BindError` carries `details: List[BindErrorDetail]` (ADR-019), but
  the type checker `QueryBinder.bind` reported at most one error: every
  combinator was a `for`-comprehension over `Either[List[TypeCheckError], _]`,
  and every failure was a one-element list, so the first failing subtree stopped
  the pass. The `List` type promised many; the binder delivered one.
- This was inherited behavior, not a recorded decision. No ADR governed binder
  error policy, and the sibling `TypeCatalog.collectErrors` — which validates the
  catalog — already accumulates. The two halves of the type system disagreed.
- A user with two independent mistakes in one query saw only the first, fixed
  it, re-ran, and only then saw the second.
- Accumulating everywhere is wrong: most binder steps thread the environment
  (the running map from variable name to inferred sort) from one result into the
  next input. Running a later step against a failed earlier step's incomplete
  environment manufactures cascade errors — a second error that exists only
  because the first left a variable unbound, pointing at nothing the user did
  wrong on its own.

---

## Decision

### 1. Accumulate only where two subtrees take the same input independently

The binary connectives (`/\`, `\/`, `=>`, `<=>`) are the one point in the binder
where two subtrees bind against the **same** environment and neither reads the
other's output. `bindBinary` already passes the same `env` to both sides. That is
the accumulation site, and it is the only one.

Everything else stays sequential because the environment threads: the top-level
`range → scope → answer-vars` chain, the term-after-term fold inside an argument
list, and a quantifier body all consume an environment an earlier step produced.

### 2. A strict accumulating product over the error channel

```scala
private def both[A, B](
  ea: Either[List[TypeCheckError], A],
  eb: Either[List[TypeCheckError], B]
): Either[List[TypeCheckError], (A, B)] =
  (ea, eb) match
    case (Right(a), Right(b)) => Right((a, b))
    case (Left(e1), Left(e2)) => Left(e1 ++ e2)
    case (Left(e1), Right(_)) => Left(e1)
    case (Right(_), Left(e2)) => Left(e2)
```

`eb` is strict — evaluated unconditionally. A by-name second argument would
re-introduce short-circuiting, which is the behavior this decision removes.

```scala
private def bindBinary(p, q, env, catalog, mk) =
  both(bindFormula(p, env, catalog), bindFormula(q, env, catalog)).flatMap {
    case ((boundP, leftEnv), (boundQ, rightEnv)) =>
      mergeEnvs(leftEnv, rightEnv).map(m => (mk(boundP, boundQ), m))
  }
```

### 3. The cascade policy is structural, not a suppression pass

Because accumulation is confined to same-input siblings, cascade errors cannot
arise: the right side of a connective already bound against `env`, never against
the left side's output, so running it after the left side fails feeds it exactly
the input it would have received anyway. There is no need to track unresolved
variables or filter follow-on errors — the boundary itself guarantees every
accumulated error is an independent mistake. Extending accumulation into
env-threaded points (argument lists, the top sequence) would break this property
and require an explicit suppression policy; that is out of scope here (see
Alternatives Rejected).

### 4. `mergeEnvs` accumulates its conflicts

`mergeEnvs` runs only when both connective sides already type-checked; each
variable is judged against the same `(left, right)` pair, so every conflicting
variable is an independent same-input judgment and all conflicts accumulate.
Keys are sorted so the error order is deterministic across the JVM and JS
platforms.

## Code Smells

### ❌ A by-name second argument in the accumulator

```scala
// BAD: `eb` by-name short-circuits — the second side is never evaluated when
// the first fails, so nothing accumulates.
def both[A, B](ea: Either[List[E], A], eb: => Either[List[E], B]) = ea.flatMap(...)

// GOOD: strict `eb`, evaluated unconditionally, errors concatenated.
def both[A, B](ea: Either[List[E], A], eb: Either[List[E], B]) = (ea, eb) match ...
```

### ❌ Accumulating across an env-threaded point

```scala
// BAD: scope binds against the range's output env; accumulating range+scope
// reports cascade errors that only exist because the range failed.
both(bindFormula(range, env, cat), bindFormula(scope, envAfterRange, cat))

// GOOD: the top sequence stays a `for`-comprehension — one failure stops it.
for
  (boundRange, envAfterRange) <- bindFormula(range, env, cat)
  (boundScope, _)             <- bindFormula(scope, envAfterRange, cat)
yield ...
```

### ❌ Short-circuiting the merge-conflict check

```scala
// BAD: a fold that returns Left on the first conflict hides the rest.
keys.foldLeft(Right(Map.empty))((acc, k) => acc.flatMap(m => ... Left(oneConflict)))

// GOOD: collect every conflicting key, then decide.
val conflicts = keys.collect { case k if left.get(k).exists(a => right.get(k).exists(_ != a)) => ... }
conflicts match { case Nil => Right(merged); case cs => Left(cs) }
```

## Cross-ADR Relationship

- **ADR-004.** Accumulation is internal to `vql.typed`; the facade still projects
  each `TypeCheckError` to a `BindErrorDetail`. No import direction changes.
- **ADR-006.** No new ADT; `TypeCheckError` and `BindErrorDetail` are unchanged.
- **ADR-012.** Still `Either[List[TypeCheckError], _]` on the left channel; only
  the list length changes, never the `require`-vs-`Either` split.
- **ADR-014.** `TypeNotQuantifiable` is raised at sequential points (the
  quantified variable and the quantifier body), which stay short-circuit, so its
  emission is unchanged.
- **ADR-017.** `bindSatisfyingFormula`'s documented ordered failure chain
  (`UnconstrainedVar` → `UnexpectedFreeVar` → `TypeNotQuantifiable`) runs after
  `bindFormula` returns and is a sequential chain; it is unaffected.
- **ADR-019.** This decision fills the multi-element `details` list ADR-019
  already types. The derived `messages` maps over however many details there are.

## Alternatives Rejected

### Accumulate into argument lists and the top-level sequence
- **What:** push accumulation past the binary connectives — bind every term of an
  argument list, and the `range/scope/answer-vars` chain, collecting across them.
- **Why rejected:** those points thread the environment, so a failure in one
  leaves a variable unbound and every downstream step binding against the partial
  environment produces cascade errors — a bad `Loss` literal in one argument
  turning into a spurious "unconstrained variable" elsewhere. Reporting those is
  worse than reporting one real error, and suppressing them requires tracking
  which variables a failure left unresolved and filtering errors that follow only
  from them. The marginal gain (two mistakes crammed into a single atom or the
  scope-after-range case) does not justify that policy. If real queries show
  demand, it becomes its own decision with an explicit cascade-suppression pass.

### Leave the binder short-circuiting
- **What:** keep the inherited one-error behavior; let register call
  `QueryBinder.bind` per subtree if it wants more.
- **Why rejected:** it keeps `List[TypeCheckError]` dishonest, keeps the type
  checker inconsistent with `TypeCatalog.collectErrors`, and keeps AC-2 from the
  sort-fidelity contract unprovable through the pipeline. The accumulation site is
  a single combinator swap with no cascade risk — there is no cost that buys.
