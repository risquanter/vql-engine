# ADR-012: Error Channel Policy — `require` vs `Either`

**Status:** Accepted  
**Date:** 2026-03-26  
**Tags:** error-handling, Either, require, preconditions, typed-errors

---

## Context

- Two distinct failure modes exist: **programmer error** (broken invariants, impossible states) and **operational failure** (missing relation, bad input, I/O error)
- Scala's `require()` throws `IllegalArgumentException` — untyped, unchecked, invisible in the signature
- `Either[QueryError, A]` makes failure explicit in the return type — callers must handle it
- The OCaml-ported foundation layer (ADR-007 scope) uses exceptions for internal control flow by design; this is a known special case, not a contradiction — see §Relationship to ADR-007 below
- Constructor invariants (e.g. "arity ≥ 1", "name non-empty") are properties of the **type itself** — once constructed, the value is guaranteed valid
- Operational methods (e.g. "look up relation X in the KB") depend on **external state** the caller does not control

---

## Decision

### 1. `require()` — Construction-Time Invariants Only

Use `require()` for invariants that define what a value **is**. These are preconditions on the type's own construction — a violation is a programming error, not a recoverable condition.

```scala
// ✅ require: the opaque type itself guarantees non-empty
opaque type SymbolName = String
object SymbolName:
  def apply(value: String): SymbolName =
    require(value.nonEmpty, "SymbolName must be non-empty")
    value

// ✅ require: structural invariant of a smart constructor
def mkAtLeast(k: Int, n: Int, tol: Double = 0.1): Quantifier =
  require(n > 0, "Denominator must be positive")
  require(k >= 0 && k <= n, s"Numerator must be in [0, n]: got k=$k, n=$n")
  AtLeast(k, n, tol)
```

### 2. `Either[QueryError, A]` — Operational Failures

Use `Either` for any method whose success depends on state external to its arguments. The caller cannot guarantee the precondition holds without inspecting the state first — that inspection-then-act pattern is the duplication `Either` eliminates.

```scala
// ✅ Either: success depends on model state (is the sort's domain registered?)
def evaluate(query: BoundQuery, model: RuntimeModel, ...): Either[QueryError, EvaluationOutput[Value]]

// ✅ Either: success depends on catalog/dispatcher agreement, checked once at construction
def apply(catalog: TypeCatalog, model: RuntimeModel): Either[QueryError, FolModel]
```

### 3. `require()` as Belt-and-Suspenders Behind `Either` Boundaries

A `require()` MAY remain as a redundant safety net inside a method that is already validated by an `Either`-returning caller. The `require` must never be the **primary or only** error handling — it exists to catch invariant violations that "should be impossible".

```scala
// ✅ Belt-and-suspenders: the estimator produces a proportion in [0, 1] (Either
//    path), then delegates to accepts() whose require re-checks that invariant
def accepts(q: Quantifier, prop: Double, epsilon: Double): Boolean =
  require(prop >= 0.0 && prop <= 1.0, s"Proportion must be in [0, 1]: got $prop")
  // ...
```

### 4. Decision Criteria — Quick Reference

| Question | `require()` | `Either` |
|---|---|---|
| Can the caller guarantee the precondition at the call site? | Yes | No |
| Does success depend on external/mutable state? | No | Yes |
| Is failure a programming error or a runtime condition? | Programming error | Runtime condition |
| Would migrating to Either force every constructor call to unwrap? | Yes → keep `require` | No |
| Is the check inside OCaml-ported code (ADR-007 scope)? | Use `throw` (C2, C12) | N/A |

## Relationship to ADR-007

ADR-007 mandates exception-based control flow in the OCaml-ported foundation layer (parser combinators, lexer, FOL semantics, printer). That mandate is **not in conflict** with this ADR:

- ADR-007 applies to a **closed set of files** listed in its scope table (Tiers 1–3). Those files use `throw` for internal backtracking and `failwith`-style signalling (C2/C12). The public string-input boundary in that layer — `FOLParser.{parse, defaultParser, parseWithLexer}` — catches those throws once and returns `Either[parser.ParseError, Formula[FOL]]`, so no exception escapes the public API (C2). `parser.ParseError` is foundation-local (no `vql.*` import), keeping the FOL core independently usable (ADR-004).
- ADR-012 applies to **all other code** — the `vql/` vague layer (parser, typed pipeline, quantifier, sampling), which returns `Either[QueryError, A]`.
- The vague layer calls only the `Either`-returning FOL entry, so foundation throws are never caught ad hoc inside vague code. A consumer needing `QueryError` maps `parser.ParseError` at its own boundary.

**Summary:** ADR-007 governs the OCaml core's internals; ADR-012 governs everything else. The two `Either` boundaries are `FOLParser.parse` (foundation) and `VagueQueryParser.parse` (vague layer).

## Code Smells

### ❌ `require()` as the Only Guard on State-Dependent Operations

```scala
// BAD: success depends on model state, but require throws untyped
def domainOf(model: RuntimeModel, sort: TypeId): Set[Value] =
  model.domains.getOrElse(sort,
    throw new IllegalArgumentException(s"No domain for sort: ${sort.value}"))

// GOOD: state-dependent failure is explicit in the type
def domainOf(model: RuntimeModel, sort: TypeId): Either[QueryError, Set[Value]] =
  model.domains.get(sort) match
    case None      => Left(QueryError.DomainNotFoundError(sort.value, model.domains.keySet.map(_.value)))
    case Some(dom) => Right(dom)
```

### ❌ `Either` for Trivial Construction Invariants

```scala
// BAD: forces every call site to unwrap for a trivial invariant
def apply(value: String): Either[QueryError, SymbolName] =
  if value.isEmpty then Left(QueryError.ValidationError("empty", "name"))
  else Right(value)

// GOOD: require — caller controls the input, failure is programming error
def apply(value: String): SymbolName =
  require(value.nonEmpty, "SymbolName must be non-empty")
  value
```

### ❌ Throwing in a Non-OCaml Method That Could Return Either

```scala
// BAD: private helper converts Left to throw, public method catches it back
private def bindOrThrow(query: ParsedQuery, catalog: TypeCatalog): BoundQuery =
  QueryBinder.bind(query, catalog) match
    case Right(bound) => bound
    case Left(errors) => throw QueryException(...)  // throw-to-catch trampoline
// ...
try Right(TypedSemantics.evaluate(bindOrThrow(query, catalog), model))
catch case e: QueryException => Left(e.error)

// GOOD: compose Either directly
def evaluateTyped(query: ParsedQuery, folModel: FolModel): Either[QueryError, EvaluationOutput[Value]] =
  for
    bound  <- bindTyped(query, folModel.catalog)
    output <- TypedSemantics.evaluate(bound, folModel.model)
  yield output
```

## Implementation

| Location | Pattern |
|----------|---------|
| `TypeId.apply`, `SymbolName.apply` | `require` — construction invariant (non-empty) |
| `VagueQuantifier` case classes | `require` — construction invariant |
| `Quantifier.mk*` smart constructors | `require` — construction invariant |
| `Quantifier.accepts` | `require` — belt-and-suspenders (values computed internally) |
| `Domain(elements)` | `require` — construction invariant (OCaml core, ADR-007) |
| `SamplingParams`, `HDRSampler`, `NormalApprox` | `require` — construction invariant |
| `TypeCatalog.apply` / `FolModel.apply` | `Either` — construction depends on catalog/dispatcher agreement |
| `TypedSemantics.evaluate` | `Either` — success depends on model state (`DomainNotFoundError`) |
